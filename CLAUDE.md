# racecraft — правила работы

Проект ведут двое (@levalovushka и @dmitrynishchev), асинхронно, часто через Claude. Описание проекта — в [README.md](README.md).

## Git
- Никогда не пушить в `main` напрямую и не делать force push в `main`. `main` сразу уходит на сайт через Netlify.
- Одна задача — одна ветка от свежего `main`: `git switch main && git pull && git switch -c <тип>/<коротко>` (`feat/`, `fix/`, `docs/`, `chore/`). Облачная сессия Claude Code получает ветку `claude/<имя>` и пушит только в неё — это нормально, дальше тот же путь через PR.
- Готово → push ветки и pull request в `main`. Сливает автор после зелёной проверки CI, способ — squash merge.
- Сессия Claude, закончив задачу, сама пушит ветку и открывает PR в `main`; сливает человек. Прямой push в `main` запрещён и для Claude, даже если попросили «выкатить»: выкатка = слияние PR.
- Каждый PR получает Deploy Preview от Netlify (ссылка в комментарии бота) — дизайн и поведение смотрим там до слияния.
- PR маленькие и короткоживущие (1–2 дня). Длинная работа — регулярно подтягивать `main` в ветку (`git merge origin/main`).
- Конфликт при слиянии с чужими изменениями — не выбирать «свою версию» вслепую: разобраться, что поменял второй, сохранить оба смысла; если неясно — спросить в PR.
- Не переписывать историю уже запушенных веток, в которых может работать второй человек. Чужую ветку — только новыми коммитами или merge, без rebase и force push.

## Перед PR
`cd sim && npm run lint && npm run build` — должно проходить. Это же проверяет CI ([.github/workflows/ci.yml](.github/workflows/ci.yml)).

Менялся `sim/src/engine/` — прогнать `npm run validate` (нужен локальный `data/races.json`, в CI его нет) и сравнить с таблицей в [docs/SIMULATOR.md](docs/SIMULATOR.md) §12.

## Секреты
Репозиторий публичный: никаких токенов, паролей и ключей в коде и коммитах. Данные заездов (`data/`) в git не попадают.
